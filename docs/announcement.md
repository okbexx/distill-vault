# 蒸馏塔 distill-vault：一个人的知识库运行时

我做 distill-vault，不是因为世界上缺一个新的笔记工具，而是因为我越来越清楚地感受到：知识库这件事，真正缺的从来不是输入框、编辑器或者双链视图。

真正的问题是，知识库越用越乱。

尤其当你一边用 Obsidian 管理资料，一边又在用各种 AI 工具链做检索、写作、分析和项目推进时，这种混乱会被放大得非常明显。今天记了一篇来源，明天整理出一个概念，后天做了一个决策，再过几周回头看，链接还在，文件也都在，但上下文已经散了：哪些结论来自原始来源，哪些只是临时判断，哪些项目正在依赖某个概念，哪些文档已经过时——很难说清。

写代码时我们早就接受了一套基础设施：有编译器检查语法，有测试验证行为，有 CI 保证改动不会悄悄把别的地方搞坏。可知识库呢？大多数时候，它只有“存进去”这一步。你可以无限记录、无限连接、无限堆积，但系统不会告诉你结构是否健康，不会提示链接是否失效，也不会在你改动一个核心概念时告诉你：下游哪些项目和输出可能已经受影响。

这就是 distill-vault 想解决的问题。

它不是又一个笔记插件，也不是给 Obsidian 侧边栏再加一个按钮。它更像是把知识库当成代码仓库来治理：把原本松散的 Markdown 文件，变成一个可以扫描、解析、建图、检查、分析、导出，并且能被 AI Agent 直接操作的知识库运行时。

## 知识库应该是 runtime，不是 storage

我现在越来越不喜欢把个人知识库理解成“存储系统”。

“storage” 这个词的问题在于，它默认你最重要的动作是保存：把资料存起来，把想法记下来，把会议纪要归档，把网页摘录收集到仓库里。它当然有价值，但它只解决了“别丢”。

而对一个持续和 AI 协作的开发者来说，真正重要的是“能不能运行”。

代码为什么能运行？因为它不是一堆源文件的静态堆积，而是一套有约束、有结构、有检查、有反馈的系统。你改了一行代码，编译器会告诉你类型对不对；你重构一个接口，测试会告诉你行为有没有破；你发起提交，CI 会替你把一整条链路跑一遍。

知识库大多没有这些东西。

你改了一个概念定义，不知道哪些项目页还在引用旧说法；你删掉一篇来源，不知道哪些决策失去了证据支撑；你让 AI 去“基于我的知识库回答”，却无法确认它拿到的是原始来源、整理后的概念，还是某篇早就过期的输出。

所以 distill-vault 的核心思路很直接：知识库不应该只是 storage，而应该是 runtime。

这个 runtime 至少要做三件事：

- 像编译器一样，把松散文本编译成结构化对象和关系。
- 像测试系统一样，检查知识库的健康状态、结构缺陷和潜在风险。
- 像 CI 一样，在每次变更后增量运行，持续维护整个知识系统的可用性。

如果用一句更短的话概括，distill-vault 就是知识库的“编译器 + 测试 + CI”。

## 技术架构：把知识治理做成一条可执行流水线

这个项目的技术灵感，来自我非常认同的一类系统设计：不是围绕“文档编辑”做功能，而是围绕“运行时治理”做能力。这里面有不少思路借鉴了 GitNexus 那条路线——图数据库、Pipeline DAG、MCP、影响分析——但我把它们移植到了个人知识库这个问题域里。

整个 distill-vault 的主干，是一个 **6 阶段 Pipeline DAG**：

`Scan → Parse → Graph → Analyze → Promote → Export`

如果把它类比成 CI/CD，会很好理解：

- **Scan**：扫描 vault，做内容哈希和检查点记录，判断哪些文件发生变化。
- **Parse**：并行解析 Markdown、frontmatter、wikilink 和对象字段。
- **Graph**：把对象和关系写入可重建的 SQLite + FTS5 投影，形成稳定的知识图谱索引。
- **Analyze**：做健康检查、社区发现、影响分析、过时检测。
- **Promote**：把“来源”向“概念 / 决策 / 输出”做可审查的晋升建议。
- **Export**：导出报告、索引和给 Agent 使用的运行面。

我刻意把它做成 DAG，而不是写死的一串脚本。原因很简单：知识库不是一次性构建物，它需要不断重跑，而且要支持增量执行、失败恢复和局部更新。这里的运行方式更接近 CI，而不是“点一下插件按钮”。

底层索引在 v1 中使用 **SQLite + FTS5**。Markdown 和 Git 仍是唯一事实源，数据库只承载可删除、可重建的对象、类型化边和全文检索投影。来源、项目、概念、实体、决策、约束、输出这些对象，以及它们之间通过 wikilink 和 frontmatter 形成的关系，仍然按图结构提供类型化查询与遍历。

一旦有了图，很多以前只能靠人脑维护的事情就可以落地成查询和分析：

- 一个概念被哪些项目复用？
- 某个决策的证据链来自哪些来源？
- 哪些对象是孤儿节点？
- 哪些约束已经长期未被引用，可能过时？

检索层我没有走单一路线，而是做了 **混合搜索**。关键词检索适合找明确术语，语义检索适合找“我大概记得这个意思，但不记得原词”的内容，所以最终用的是 BM25 和语义搜索结合，再做融合排序。对个人知识库来说，这种体验很重要，因为人脑回忆上下文时，经常不是按精确关键字来的。

另一个我很在意的接口层，是 **MCP 协议**。

如果知识库要成为 runtime，它就不能只服务于“人打开 Obsidian 看一眼”，还必须服务于 AI Agent 的直接调用。distill-vault 里我把一组核心能力暴露成 MCP 工具：查 vault 状态、跑混合搜索、看对象上下文、执行图查询、做上下游影响分析、检测变更、触发 pipeline。这样一来，Agent 不是“读几篇 Markdown 猜测上下文”，而是真的在操作一套有索引、有结构、有分析能力的知识系统。

最后是我认为最关键、也最能体现 runtime 价值的一点：**影响分析**。

代码世界里，大家都知道改公共接口要先看 blast radius。知识库其实也一样。你修改了一个核心概念定义，或者把某条约束状态改掉，这不只是“改了一篇笔记”，而是在改整个系统的一部分事实。distill-vault 会沿着图做 upstream / downstream 分析，告诉你哪些项目、决策、输出可能直接或间接受影响。对长期维护个人知识库的人来说，这种反馈非常重要，因为它第一次让“改知识”这件事具备了可观测性。

## 真实数据：这不是 demo，而是一套跑起来的系统

我不太喜欢用空泛的“支持企业级”来介绍项目，所以直接说目前已经跑出来的数据。

在 README 里，distill-vault 当前给出的测试和样本结果包括：

- 6 阶段 Pipeline DAG 已经完整打通。
- SQLite + FTS5 作为本地对象、关系和全文检索投影，Schema 版本为 `1`。
- MCP Server 通过 stdio 暴露了 `16` 个工具。
- 在一份真实 vault 上，跑出了 `234` 个对象、`1,295` 条边、`55` 个社区，modularity 为 `0.544`。
- 单元测试目前是 `19/19` 通过。

这些数字当然还不算“大”，但它们足够说明一件事：这不是“想法验证式 demo”，而是一套从对象模型、索引构建、图查询、检索、健康检查到 Agent 接入都已经贯通的产品原型，而且它是在真实知识库结构上跑起来的。

更重要的是，这些数字背后代表的是一套工作方式：我可以把一个 Obsidian vault 当成可计算、可检查、可查询、可演进的系统，而不是只能人工维护的一堆笔记。

## 我是怎么做的：一个人，加上 AI，把工程做完整

这个项目对我自己来说，最有意思的部分其实不只是“做了什么”，而是“怎么做的”。

它基本就是蒸馏塔这个品牌想表达的那句话：**一个人的 AI 工作流**。

我不是先拉团队、拆岗位，再按传统分工推进；而是一个人带着 AI，把调研、设计、实现、测试、修正、文档全部串起来。调研阶段，我会先把知识库治理、图数据库、检索方案、Agent 接口这些方向拆成问题；设计阶段，把对象模型、Pipeline 阶段划分、图结构和命令行接口逐步定下来；实现阶段，让 AI 参与脚手架、样板代码、查询逻辑、测试用例和文档整理；测试阶段，再反过来用自动化和真实数据把系统压一遍。

这里面 AI 不是“帮我写点代码”的附属品，而是整个开发流的一部分。它参与信息蒸馏、方案对比、代码生成、回归验证，也参与我自己的思考过程。但最终的产品约束、架构取舍和问题定义，还是得由人来拍板。

我一直觉得，独立开发真正稀缺的不是写代码速度，而是把复杂问题持续收束成一套能落地、能迭代、能验证的系统能力。distill-vault 某种意义上也是这个过程的副产品：一边做“一个人的 AI 工作流”，一边把这个工作流反过来沉淀到知识库 runtime 里。

## Quick Start

如果你本来就在用 Obsidian，而且也希望自己的知识库能被 AI 更可靠地使用，可以直接从最基本的命令开始：

```bash
# 安装
pip install -e .

# 进入你的 Obsidian vault
cd ~/my-vault

# 查看知识库状态
distill status

# 跑完整 6 阶段 pipeline
distill run

# 做混合搜索
distill search "Agent工作流" --mode hybrid

# 做结构检查并自动修复
distill lint --fix

# 增量运行
distill run --incremental

# 启动 Web UI
distill web --port 8420

# 启动 MCP Server，供 AI Agent 接入
python -m distill.mcp_server --vault ~/my-vault
```

如果你只记一个使用顺序，我建议是：先 `status` 看清现状，再 `run` 建索引，然后用 `search`、`lint` 和 `MCP` 真正把它接入到日常工作流里。只有当知识库开始参与你的查询、决策和项目推进，它才从 storage 变成 runtime。

## 结尾

distill-vault 是蒸馏塔 / Distill 这条产品线里，我自己非常想长期打磨的一块基础设施。

它服务的不是“爱记笔记的人”，而是那类已经在用 Obsidian 管理个人知识，同时又在用 AI 工具链做开发、研究和写作的人。对这类用户来说，真正的问题不是“怎么再多记一点”，而是“怎么让知识库持续可运行、可验证、可协作”。
